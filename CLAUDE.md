# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

Absensi SPPG is an offline-first attendance/payroll system with two Bun/Next.js 16 + Tauri v2 workspaces that share nearly identical application code:

- `web-desktop/` — Next.js Web (Vercel/Node) + Turso LibSQL, and a Tauri Desktop (Windows/Mac/Linux) build using static export.
- `mobile/` — Tauri Mobile (Android APK, iOS) build, static export only, targeting the same backend.

Both workspaces embed a Rust/SQLite local database and sync bidirectionally with a shared LibSQL cloud database. There is no server component on Desktop/Mobile — they talk to the database directly (2-tier architecture).

**Two database providers.** The remote endpoint is either managed **Turso Cloud** or a **self-hosted libSQL server** (`sqld`/`libsql-server`) on the customer's own LAN machine, NAS, or VPS. Both speak the same Hrana HTTP pipeline, so the Rust client is unchanged; only address validation differs. The choice is stored explicitly as `TursoConfig.provider` (`turso` | `self_hosted` | `local_file`) — never inferred from the URL shape — alongside `allow_insecure_transport`. `normalize_database_url` in `turso.rs` is the single gate: Turso requires HTTPS, self-hosted may use plain HTTP to private-network hosts even in release builds, and plain HTTP to a public host needs the explicit opt-in flag. Auth tokens are required for Turso and for publicly-reachable HTTPS self-hosted servers, and optional for a libSQL server on a private network.

**`web-desktop` is the canonical source for shared code.** `mobile/src/lib/*` and several `mobile/src-tauri/src/mobile/*.rs` files are generated copies produced by `mobile/scripts/sync-frontend-lib.ts` and `mobile/scripts/sync-rust-modules.ts` (the Rust sync also rewrites `Desktop*` → `Mobile*` identifiers and `crate::desktop` → `crate::mobile`). Edit the `web-desktop` originals first, then re-run these scripts from `mobile/` — do not hand-edit the generated files, changes will be silently overwritten on next sync.

## Commands

Run from the repo root unless noted. The root has no build of its own — it only orchestrates the two workspaces. Its `package.json`/`tsconfig.json` exist solely to type the audit scripts in `scripts/` (`@types/bun`, `@types/node`); no compiler runs there and nothing is bundled from it. Application dependencies belong in `web-desktop/` or `mobile/`, never here.

```bash
# Full quality gate across both workspaces (schema audit + sync contract audit + lint + typecheck + tests, both workspaces)
bun run check:quick

# Same as above, plus Rust cargo tests in both workspaces
bun run check

# Root-only: verify DB schema matches storage.rs/turso.rs/db-schema.ts across both workspaces
bun run audit:schema

# Root-only: verify outbox producers only use the canonical sync routes
bun run audit:contract

# Reset superadmin password / clear rate limits (web-desktop)
bun run reset:superadmin
```

Per-workspace (run inside `web-desktop/` or `mobile/`; scripts are identical in both):

```bash
bun dev                  # Next.js dev server (webpack)
bun run lint             # biome check .
bun run format           # biome format --write
bunx tsc --noEmit        # typecheck
bun run test             # runs every src/**/*.test.ts(x) via scripts/run-tests.ts
bun test path/to/file.test.ts   # run a single test file directly (bun:test)
bun run test:rust        # cargo test --manifest-path src-tauri/Cargo.toml
cargo test --manifest-path src-tauri/Cargo.toml <test_name>   # single Rust test
bun run check:quick      # lint + typecheck + test (this workspace only)
bun run check            # + test:rust
```

Builds:

```bash
# web-desktop
bun run build:web        # Next.js server build for Vercel
bun run build:desktop    # static export to out/ for Tauri Desktop
bun run tauri:build      # packages the Desktop installer (runs build:desktop first)
bun run tauri:preview    # tauri dev against src-tauri/tauri.preview.conf.json, --no-watch

# mobile
bun run build:mobile     # static export to out/ for Tauri Mobile
bun run tauri:android:build:arm64
bun run tauri:ios:build
```

`SPPG_BUILD_TARGET` / `NEXT_PUBLIC_SPPG_RUNTIME` (`web` | `desktop` | `mobile`) select the target at build/dev time — set by the scripts above, not manually.

Quality-gate discipline: run `bun run check:quick` **once**, at the end, after a change is fully written — not repeatedly mid-edit.

## Architecture

**Runtime detection & Gateway pattern.** `isDesktopRuntime()` (`src/lib/runtime/app-runtime.ts`) checks `NEXT_PUBLIC_SPPG_RUNTIME` / `window.__TAURI_INTERNALS__` to decide, at call time, whether the app is running as a Tauri app or a plain web page. UI components never call `invoke()` or `fetch("/api/...")` directly — every data operation goes through a module in `src/lib/gateways/*.ts`, which branches: Tauri → `invokeDesktop()`/`invokeMobile()` (Rust IPC command), web → `requestWebApi()` (Next.js route handler under `src/app/api/`).

**Static export constraint.** Desktop and Mobile Tauri builds use Next.js `output: "export"`, which cannot serve dynamic `GET` route handlers. Every handler under `src/app/api/**/route.ts` uses `POST` (commonly a `POST /.../query` endpoint for reads) or `PUT`/`PATCH`/`DELETE` — never `GET`.

**Rust backend layering** (`src-tauri/src/desktop/*` or `src-tauri/src/mobile/*`): `commands.rs` (thin Tauri command handlers, auth/session checks) → `operational.rs`/`administration.rs`/`scanner.rs` (business logic) → `storage.rs` (local SQLite) / `turso.rs` (cloud LibSQL pipeline client). `secrets.rs` holds the AES-256-GCM + Argon2id credential vault; `time_policy.rs` is the sole source of truth for attendance timestamps (never trust client JS `Date`); `sync.rs` implements the outbox/snapshot sync engine.

**Sync engine (zero schema drift).** Table/column definitions must stay identical across four layers: Rust `SNAPSHOT_TABLES` in `sync.rs`, SQLite DDL in `storage.rs`, server schema in `web-desktop/src/lib/db-schema.ts` + `db-migrations.ts`, and the Zod validators in `sync-schema.ts`. Furthermore, Rust `turso.rs:625` defines `SNAPSHOT_SOURCES` which MUST stay in 100% parity with `SNAPSHOT_TABLES` (all 30 tables) — it is the single source for generating snapshot SELECT queries AND installing cloud `sync_pulse` triggers. Local mutations are queued in `desktop_sync_outbox` and pushed under one of the 62 canonical hyphen-case routes (e.g. `attendance/scan`, `company-profile/update`); `bun run audit:contract` enforces this. The list itself is `CANONICAL_SYNC_ROUTES` in `sync.rs`. Both counts drift with every phase — count them in the code rather than trusting these numbers. Pulls apply cloud snapshots into local SQLite without clobbering rows that still have a pending/conflict outbox entry.

**Attendance priority is enforced at the cloud, not just locally.** `apply_event_to_turso` is preceded by `assert_attendance_precondition`, which rejects a push that would overwrite a `Koreksi Admin` row from a lower-priority source, and rejects any event whose `attendanceBaseUpdatedAt` no longer matches the cloud's `update_terakhir`. That field is produced by every client and validated by `sync-schema.ts`; before this it was simply never read on the Turso path.

**One cloud database, two provisioning paths.** The same Turso database is created either by Rust `turso.rs::ensure_schema` (bootstrap from Desktop/Mobile) or by TS `db-schema.ts` + `db-migrations.ts` (the web app). Both must produce identical tables and columns — `CREATE TABLE IF NOT EXISTS` never repairs a table that already exists, so a mismatch permanently breaks whichever path did not create it. `app_session`, `auth_login_rate_limit`, `role_permission_audit`, and `sync_change_log` are *web-owned*: Rust creates them only so the web keeps working, and must copy the TS definition verbatim. Columns only one side knows about go in Rust's `ensure_column` list *and* a TS `ALTER TABLE` migration, so either client heals the other's database. `bun run audit:contract` diffs the two implementations and checks that Rust provisioning creates every table `isDatabaseSchemaReady` counts.

Two things must never cross the sync boundary, and `bun run audit:contract` enforces both: the device-local connection keys in `sync::DEVICE_LOCAL_SETTING_KEYS` (they live in the synced `setting_gex_system` table but decide which cloud DB *this* device talks to), and the default payroll rate rows in `payroll_seed::DEFAULT_RATE_IDS`. The default rate tables (`overtime_tier_rules`, `tax_rules`, `bpjs_rules`) are seeded from the single file `desktop/payroll_seed.rs`, used by both `storage.rs` (local) and `turso.rs` (cloud) — never re-write those seeds anywhere else.

Shared gateways run on both builds, but the two Rust binaries do not register the same commands (mobile has no payroll administration commands). A gateway function reachable from mobile UI must branch on `isMobileRuntime()` to a command mobile actually registers; the contract audit walks gateway call graphs from `src/app`/`src/components` to catch this.

Pulls are incremental: the cloud table `sync_pulse` holds a per-table change counter driven by SQLite triggers, so writes from *any* path — Desktop/Mobile push, the Next.js web route handlers that write straight to Turso, or manual edits — bump it. A sync cycle first probes `sync_pulse`, compares against the local `desktop_sync_table_cursor`, and fetches only the tables whose counters moved (often none). Within a fetched table, rows whose SHA-256 matches `desktop_entity_revision.payload_hash` are skipped without a write. A payload key that is absent from a snapshot means "unchanged", not "empty" — `apply_table` must skip it entirely, `delete_missing` included. A failed push never aborts the pull; it is reported via `DesktopSyncStatus.push_error`. Details: `.agents/skills/absensi-sppg-rules/references/02-sync-canonical-and-outbox.md` and `03-schema-4layer-consistency.md`.

**Akun operator & "Lupa Password".** `master_operator` punya kolom `email` dan `no_hp` (schema versi 11). Keduanya NULL-able di DDL supaya baris operator lama tidak rusak, tetapi WAJIB pada setiap `insertOperator`/`editOperator` dan pada bootstrap Superadmin — aturannya ada di satu tempat, `src/lib/operators/contact.ts`, dengan cerminan Rust (`normalize_operator_email`/`normalize_operator_phone`/`validate_operator_contact` di `turso.rs`) yang diuji agar tetap sama. Nomor HP selalu disimpan kanonik `+62…`; email selalu lowercase karena index uniknya memakai `LOWER(email)`.

Alur pemulihan password memakai dua tabel cloud-only baru (tidak pernah masuk `SNAPSHOT_TABLES`): `password_reset_request` (bukti foto + hash token, jangan direplikasi ke SQLite tiap perangkat) dan `app_mail_config` (kunci API penyedia email). Langkah intinya — `lookup` → `confirm` → `verify` → `inspect-token` → `complete`, ditambah `route` dan `recover-with-code` — dilayani `POST /api/password-reset` di Web dan command `desktop_password_reset_*` di Desktop/Mobile; seluruhnya tanpa sesi login, dijaga rate limit `auth_login_rate_limit`, urutan tantangan acak yang hanya diketahui database, dan token sekali pakai berumur 30 menit.

**Token itu punya DUA jalur penyerahan, dan keempat implementasinya wajib sepakat.** `password_reset_route` / `resolvePasswordResetRoute` memilihnya: nilai eksplisit di `setting_gex_system` menang lebih dulu, baru `app_mail_config.is_active` dipakai sebagai bawaan — email bila aktif, `in_app` bila tidak. Urutan itu tidak boleh dibalik: satu database yang sama bisa dilayani Web dan Desktop bergantian, dan bila keduanya menyimpulkan jalur berbeda sebuah permintaan akan menunggu persetujuan yang tidak pernah diminta. Pada jalur `in_app`, `verify` **tidak membuat token sama sekali** — barisnya tetap `Menunggu Verifikasi` dengan `delivery_status = 'Menunggu Persetujuan'`, dan tokennya baru lahir di layar peninjau saat `approve`. Kalau token dibuat lebih dulu, bentuk aslinya harus disimpan di suatu tempat sampai disetujui, sementara database hanya boleh memegang hash-nya. Cabang ini ADA karena sebelumnya email yang belum dikonfigurasi membuat pengiriman selalu gagal, dan kegagalan itu **membatalkan** permintaannya — fitur "Lupa Password" mati total di seluruh pemasangan Mode Database Lokal.

Jalur ketiga, **kode pemulihan cetak**, tidak menunggu siapa pun: delapan kode diterbitkan sekali saat provisioning Superadmin (dan bisa diterbitkan ulang dari Pengaturan), disimpan hanya sebagai hash SHA-256, dan dihapus begitu dipakai. Ini satu-satunya jalan pulih bagi Superadmin pada pemasangan tanpa jaringan — akun itu tidak punya siapa pun di atasnya yang bisa menyetujui permintaannya. `generateRecoveryCodes`/`normalizeRecoveryCode` (`src/lib/security/totp.ts`) dan `generate_recovery_codes`/`normalize_recovery_code` (`turso.rs`) **wajib tetap identik**, termasuk membuang setiap karakter non-alfanumerik: kode yang sama harus menghasilkan hash yang sama di Web maupun Desktop, karena kode yang dicetak di satu build dipakai untuk masuk lewat build yang lain. **Seluruh stempel waktu dan perbandingan kedaluwarsa di alur ini WAJIB dihitung SQLite (`datetime('now')`)**, tidak pernah `new Date()`: satu baris bisa dibuat Rust dan dibaca TypeScript, dan `new Date("2026-08-29 10:15:00")` diparsing sebagai waktu lokal.

Riwayat pengajuannya bisa ditinjau manusia di `/riwayat-reset-password` (Web/Desktop dan Mobile). MENGAJUKAN reset tidak butuh izin apa pun — alurnya memang terbuka untuk semua akun tanpa sesi; yang di-RBAC adalah **membaca, menyetujui, dan menghapus jejaknya**, lewat `password_reset.view`, `password_reset.approve`, dan `password_reset.delete`. Dua yang terakhir masuk `SENSITIVE_MUTATION_PERMISSIONS` sehingga tidak ikut paket bawaan Admin — menyetujui berarti menyerahkan kendali sebuah akun kepada orang yang sedang berdiri di depan layar, dan peninjaunya wajib memikul itu secara sadar. Foto wajah yang ia lihat adalah faktor kedua di jalur ini, dan sebenarnya lebih kuat daripada email: email hanya membuktikan penguasaan kotak masuk, bukan siapa yang meminta. Daftar riwayat tidak pernah membawa `photo_base64` — foto diambil satu per satu lewat endpoint terpisah, karena satu foto ~40 KB dan ratusan baris akan membuat balasannya puluhan megabyte.

Verifikasi wajah (`src/lib/security/face-liveness.ts`) sengaja tanpa dependensi dan tanpa berkas model: ia bekerja pada grid piksel 64×48 RGB mentah. Web mengirim frame mentah itu ke server dan server **menghitung ulang vonisnya sendiri** dengan modul yang sama; Desktop/Mobile menghitung vonis di aplikasi (di sana tidak ada server aplikasi) dan Rust memverifikasi urutan tantangannya terhadap database. Jangan mengganti modul ini dengan library ML tanpa persetujuan User — itu berarti membundel model beberapa MB dan melonggarkan CSP Desktop yang hari ini `ipc:`-only.

**Verifikasi dua langkah (TOTP).** `master_operator` menyimpan `totp_secret`, `totp_enabled`, `totp_confirmed_at`, dan `totp_recovery_codes` (schema versi 12); `app_role.require_totp` mewajibkannya per role. TOTP dipilih menggantikan penyedia identitas pihak ketiga karena **tidak butuh jaringan**: kode dihitung dari rahasia bersama dan waktu, jadi janji offline-first tidak berkurang. **SHA-1, bukan SHA-256** — Google Authenticator mengabaikan parameter `algorithm` pada URI otpauth, sehingga SHA-256 menghasilkan kode yang tidak pernah cocok tanpa pesan error apa pun. Inti algoritmenya ada di `src/lib/security/totp.ts` dengan cerminan Rust di `turso.rs`; **keduanya diuji terhadap vektor resmi RFC 4226 dan RFC 6238 yang sama** — itulah cara paritasnya dijaga tanpa bisa menjalankan aplikasi autentikator di CI. Waktu verifikasi SELALU diambil dari jam database (`strftime(%s,now)`), tidak pernah jam proses, supaya satu kode yang sah diterima sama di Web dan Desktop. Gerbang 2FA dijalankan SETELAH password terbukti benar, agar layar login tidak bisa dipakai memetakan akun mana yang memakai 2FA. Kode cadangan disimpan sebagai hash SHA-256 dan dihapus pada percobaan yang berhasil. Ketiga kode kegagalannya — `TOTP_REQUIRED`, `TOTP_INVALID`, `TOTP_ENROLLMENT_REQUIRED` — dikembalikan langsung oleh `desktop_login` dan TIDAK boleh jatuh ke lengan error umum: lengan itu memperlakukan kegagalan sebagai "cloud tidak terjangkau" dan meneruskan login ke fallback offline, yang hanya memeriksa username + password. Tanpa lengan khusus itu, perangkat yang punya cache offline melewati 2FA sepenuhnya meskipun jaringannya hidup. **Batasnya:** penegakan 2FA hanya pada login ONLINE; login yang memang berjalan offline lewat vault perangkat belum memeriksanya, karena jalur itu sudah menuntut perangkat yang pernah di-provisioning plus password yang benar.

**Keamanan absensi: foto bukti & pembatasan alamat IP (schema versi 13).** Dua fitur ini **opsional per perusahaan**. Sakelar induknya ada di Pengaturan sebagai dua setting tersinkronisasi — `scan_photo_enabled` dan `scan_ip_restriction_enabled`, bawaannya MATI supaya pemasangan berjalan tidak tiba-tiba menuntut foto setelah aplikasi diperbarui. Di bawahnya, `app_role` menyimpan `require_scan_photo` dan `require_scan_ip_allowlist` yang diatur per role di halaman Master Operator persis seperti `require_totp`. **Aturan gabungannya satu kalimat: fitur berlaku hanya bila sakelar induk hidup DAN role-nya menyalakannya** — dieja di tiga tempat yang wajib sama (`scanner.rs`, `attendance-processor.ts`, dan gerbang UI halaman scanner), dan modal Role & Akses menampilkan peringatan ketika sakelar role dinyalakan sementara fiturnya masih mati. Sakelar role dibaca dari SESI (vault offline di Desktop/Mobile, `app_session` di Web), **tidak pernah dari payload scan** — terminal yang dikuasai penyerang tidak boleh bisa mematikan kewajiban fotonya sendiri hanya dengan menghilangkan sakelarnya dari body. Statusnya dibaca lewat `desktop_get_scan_security` / `POST /api/settings/scan-security` yang hanya menuntut sesi (halaman scanner perlu tahu kapan harus menahan scan), sementara daftar alamat IP-nya hanya ikut untuk Superadmin dan hanya Superadmin yang boleh mengubahnya. Tiga hal membuat sakelar ini benar-benar sampai ke terminal yang sedang berjalan, dan ketiganya WAJIB dipertahankan: (1) role **Superadmin** ikut boleh memikul kedua kewajiban ini — nama, status, dan permission-nya tetap terkunci, tetapi menguncikan kewajibannya membuat pemegang akun Superadmin otomatis lolos dari bukti foto, dan justru akun itulah yang dipakai menguji fiturnya; (2) `update_role` (Rust maupun `role-admin.ts`) menaikkan `rbac_revision` — sesi Desktop/Mobile hanya dimuat ulang ketika angka itu berubah, jadi tanpa kenaikan itu sakelar baru berlaku setelah operatornya logout; (3) halaman scanner membaca `photoRequiredForMe` yang dihitung backend, bukan menggabungkan sendiri sakelar induk dengan objek sesi React yang dibekukan saat login.

Alur fotonya **menahan scan**. Begitu QR terbaca, terminal berhenti sejenak, mematikan kamera pemindai, membuka kamera hadap-depan (`facingMode: "user"`), menunggu wajah masuk bingkai, memotret, lalu baru mengirim absensi. Versi pertama fitur ini memotret dari kamera pemindai pada detik QR terbaca — yang terfoto justru kartu identitas yang sedang ditempelkan ke lensa, sehingga fotonya tidak membuktikan siapa yang hadir maupun di mana. Deteksi wajahnya memakai ulang detektor piksel tanpa dependensi milik "Lupa Password" (`face-liveness.ts`) dan hanya berperan sebagai pemandu: pemotretan tetap berjalan otomatis setelah 6 detik meski wajah tidak pernah terbaca, dan tombol "Ambil foto sekarang" selalu tersedia — kamera murah atau ruangan gelap tidak boleh memblokir absensi seseorang. Kamera pemindai dinyalakan lagi SETELAH absensi terkirim, dengan debounce QR disegarkan, supaya kartu yang masih menempel di lensa tidak terbaca ulang. Hanya SATU stream kamera hidup pada satu waktu: membuka kamera kedua selagi stream pemindai masih jalan membuat keduanya saling mematikan di WebView Android. Ukurannya 480x360 JPEG mutu 0,7 (~30-60 KB) lewat `src/lib/client/scan-photo.ts`. Barisnya masuk tabel `absensi_foto` dan **SENGAJA di luar `SNAPSHOT_TABLES`**: satu foto ~40 KB, sehingga menariknya lewat snapshot akan membuat tiap siklus pull berukuran puluhan megabyte di setiap perangkat. Foto ikut event kanonik `attendance/scan` yang sudah ada (kunci payload `photo`, divalidasi `sync-schema.ts` maks 2.000.000 karakter base64 — angka yang sama dieja `MAX_SCAN_PHOTO_BASE64` di `scanner.rs`), lalu dibaca satu per satu dari cloud oleh halaman `/foto-absensi`. Karena itu `absensi_foto` terdaftar pada daftar tabel non-sync lokal DAN cloud di `audit-sync-contract.ts`.

Daftar IP hidup di satu kunci `setting_gex_system` yang ikut sinkronisasi (`scan_ip_allowlist`, JSON array alamat/blok CIDR), jadi ia kebijakan kantor, bukan konfigurasi per perangkat — dan karenanya TIDAK boleh masuk `sync::DEVICE_LOCAL_SETTING_KEYS`. Penilaiannya dieja dua kali dan diuji dengan **vektor yang sama**: `src/lib/validations/ip-allowlist.ts` (Web) dan fungsi `normalize_ip_entry`/`parse_ip_allowlist`/`ip_matches_allowlist` di `scanner.rs` (Desktop/Mobile), sama seperti cara paritas TOTP dijaga. Alamat perangkat pada Desktop/Mobile dideteksi tanpa dependensi lewat trik `UdpSocket::connect` ke alamat dokumentasi RFC 5737/3849 — UDP tanpa handshake, jadi tidak ada paket yang dikirim dan tidak butuh internet; pada Web alamatnya dibaca server dari header proxy, bukan dari body. **Daftar kosong berarti BELUM DIATUR, bukan "tolak semua":** pembatasan baru berlaku setelah Superadmin mengisi jaringan yang sah, karena sakelar yang dinyalakan sebelum daftarnya terisi akan mengunci seluruh terminal di luar. Setelah daftarnya ada, dua cabang sisanya **fail-closed**: alamat yang tidak terdeteksi maupun yang tidak cocok sama-sama menolak scan, dan penolakannya tetap dicatat ke `log_scan` untuk audit tanpa membuat baris `absensi_harian` — pola yang sama dengan geofence. Aturan ini dieja dua kali (Rust dan `attendance-processor.ts`) dan wajib tetap identik.

Mengambil foto tidak butuh izin apa pun (kewajibannya ditentukan sakelar role); yang di-RBAC adalah **membaca dan menghapus** jejaknya lewat `attendance_photo.view` dan `attendance_photo.delete`, dan yang kedua masuk `SENSITIVE_MUTATION_PERMISSIONS`. Menghapus foto tidak pernah menyentuh `absensi_harian` maupun `log_scan`: yang hilang hanya bukti visualnya.

**Whitelist Shift/Divisi hari libur & upah jam hari libur (schema versi 14).** Pada tanggal yang terdaftar aktif di `tbl_hari_libur`, scanner **tidak lagi menolak semua orang**. Tabel tersinkronisasi baru `hari_libur_whitelist` menentukan siapa yang tetap boleh scan — misalnya Shift Satpam, Divisi Keamanan, Maintenance, Teknisi. Cakupannya disimpan sebagai **`kode_shift`** dan **NAMA divisi**, tidak pernah `id_shift`: id itu AUTOINCREMENT yang berbeda di tiap perangkat, sehingga whitelist yang dibuat di satu perangkat akan menunjuk shift lain begitu tersinkronisasi. Kolom `tanggal_libur` yang NULL berarti berlaku untuk SEMUA hari libur; diisi berarti hanya tanggal itu. **Daftar KOSONG berarti MENOLAK** — kebalikan dari `scan_ip_allowlist` (kosong = belum diatur = izinkan) — karena perilaku aplikasi sejak dulu adalah menolak semua scan di hari libur dan daftar kosong harus mempertahankannya. Karyawan yang memang libur tidak pernah kena Alfa: Generate Alfa sudah melewati tanggal libur, dan itu tidak diubah.

PK-nya TEXT buatan klien (`hlw-<128 bit acak>`), bukan AUTOINCREMENT, dan **sengaja TANPA UNIQUE constraint pada (`scope_type`, `scope_value`)**: dua perangkat offline boleh mendaftarkan cakupan yang sama, dan sebuah unique constraint akan membuat push sync-nya gagal PERMANEN. Duplikat tidak berbahaya karena penilaiannya OR, dan pencegahannya dilakukan di lapisan aplikasi (`assert_whitelist_unique` di `operational.rs`, `assertNoDuplicate` di `holiday-whitelist.ts`) yang bisa memberi pesan ramah. Penilaian dan normalisasinya dieja dua kali dan **diuji dengan vektor yang sama** — `src/lib/validations/holiday-whitelist.ts` (Web) dan `normalize_whitelist_scope_type`/`normalize_whitelist_scope_value`/`normalize_holiday_date`/`evaluate_holiday_scan` di `scanner.rs` (Desktop/Mobile) — persis pola paritas `ip-allowlist` dan `totp`. Cakupan selalu dibaca dari `master_data`/`tbl_shift`, **tidak pernah dari payload scan**: terminal yang dikuasai penyerang tidak boleh bisa memasukkan dirinya sendiri ke whitelist lewat body request.

Jam kerja pada tanggal libur dipisahkan sebagai **Jam Kerja Hari Libur** dan dihitung dengan jenjang lembur `HARI_LIBUR` yang sudah bisa dikonfigurasi user di menu Aturan Jenjang Lembur — sebelum ini jenjang itu tersimpan dan bisa disunting tetapi tidak pernah dibaca siapa pun, seluruh lembur selalu memakai tarif `HARI_KERJA`. Menurut PP 35/2021 tidak ada "jam kerja biasa" pada hari libur resmi, jadi nilainya adalah `jam_kerja + lembur` pada tanggal itu dan ia SENGAJA di luar `total_regular_hours`/`total_overtime_hours`. Total upah lembur = (indeks HARI_KERJA + indeks HARI_LIBUR) × rate per jam, dikalikan **sekali** supaya pembulatannya identik dengan versi satu-indeks sebelumnya. Penandanya **diturunkan lewat `LEFT JOIN tbl_hari_libur hl ON hl.tanggal = ah.tanggal AND hl.status_aktif = 1`, bukan kolom baru di `absensi_harian`** — `tbl_hari_libur.tanggal` UNIQUE sehingga join ini tidak pernah menggandakan baris, absensi lama otomatis ikut terhitung benar begitu admin melengkapi daftar hari liburnya, dan jalur sync absensi yang sensitif tidak perlu disentuh sama sekali. Hasilnya dibekukan pada `payroll_items.total_holiday_hours` dan `total_holiday_overtime_index`, jadi slip yang sudah dibuat tidak berubah ketika daftar hari libur disunting. Aturannya dieja dua kali dan wajib tetap identik: `payroll/commands.rs` (Desktop) dan `payroll-recap.ts` (Web).

**Domain specifics worth knowing before touching attendance/payroll code:**
- Overnight shifts (`jam_pulang < jam_masuk`): scan-out belongs to the next calendar day; duration = `(out_min + 1440) - in_min`.
- Attendance-record priority when reconciling sources: Admin Correction > Offline/Manual Import > Scanner Terminal > System-generated (auto-alfa).
- Payroll/tax math (PPh 21 TER/Pasal 17, BPJS) is computed in Rust using `rust_decimal`, never `f64`/JS floats; rates live in `tax_rules`/`bpjs_rules` keyed by `effective_date`, and each `payroll_runs` execution snapshots the rate it used.
- Camera lifecycle for the QR scanner must decouple unmount cleanup (`useEffect(() => () => stopCamera(), [])`, empty deps) from `visibilitychange` handling — coupling `stopCamera()` to a state-dependent effect kills the Android WebView camera immediately after open.
- **Android tidak boleh menulis ke `/storage/emulated/0/Download`.** Sejak Android 10 (scoped storage) penulisan itu ditolak, dan bentuk kegagalannya yang berbahaya: berkas tetap dibuat di folder privat, pemanggil melaporkan sukses, dan pengguna tidak pernah menemukan hasilnya. Berkas yang harus sampai ke tangan pengguna diserahkan lewat dialog Storage Access Framework (`tauri-plugin-android-fs`, hanya di-`cfg` untuk Android). WAJIB memakai `android_fs_async()`, bukan `android_fs()` — dialognya menunggu manusia, dan memblokir thread runtime selama itu membekukan seluruh antarmuka termasuk dialog yang sedang ditunggu. Pengguna yang menutup dialog adalah PEMBATALAN, bukan kegagalan, dan UI wajib membedakannya.
- **Perintah yang hanya ada di biner Mobile** hidup di modul di luar daftar salin `sync-rust-modules.ts` (`share.rs`, dan seterusnya) dan namanya WAJIB berawalan `mobile_`. Awalan itu yang dipakai `audit:contract` untuk membedakan "command hantu" dari "command khusus Mobile". Di sisi gateway bersama, panggilannya wajib berada di dalam blok `if (isMobileRuntime()) { … }` — guard POSITIF, bukan `if (!isMobileRuntime()) throw`, karena hanya bentuk itu yang dikenali `splitMobileBranch` di auditnya.
- Modal & form focus safety: In dialogs (`Modal`), callback props (`onClose`, `onSubmit`, `onChange`) MUST be stabilized via `useRef` (`onCloseRef.current = onClose`) so inline parent handlers do NOT re-trigger effects on every keystroke. Focus management (`dialogRef.current.focus()`) must run ONLY once on open transition (`[isOpen, mounted]`) and NEVER steal focus if `dialogRef.current.contains(document.activeElement)` (prevents the 1-keystroke input focus-loss bug).
- Scanner payload contract: Scanner strictly expects `id|token` format (`parts[1] == token`). Any personnel entity creation (`GURU`, `SISWA`, `PEGAWAI`) MUST generate a random `token_absensi` and write `qr_code = format!("{id}|{token}")` to `master_data`.
- No UNIQUE constraints on synced tables: Database-level `UNIQUE` constraints (besides Primary Key) on synced tables cause permanent outbox push failures (`next_retry_at = NULL`) on offline conflict. Business uniqueness must be asserted at the application layer (`assert_unique`).
- Multi-table relational soft deletes: Soft deleting child profiles (`siswa_data`, `guru_data`) must update `master_data.status_aktif = 'Nonaktif'` atomically. Cloud handlers must never hardcode status or drop relational fields (`id_shift`, `no_hp`, `lp`), preventing zombie resurrections on snapshot pull.
- Idempotent single-active state toggle: Cloud handlers for single-active entities (e.g. `akademik_tahun_ajaran.is_aktif = 1`) must deactivate others atomically: `UPDATE ... SET is_aktif = 0 WHERE id <> ?`.
- Audit script integrity: Never whitelist or loosen checks in `audit-sync-contract.ts` or `schema-audit.ts` to make tests pass. Fix the calling code instead (e.g. guard with `if (isMobileRuntime())`).
- Page-level route guards: Every private page component needs `if (!canAccessArea(user, area)) redirect("/forbidden");`.
- Strict Zod schemas: Always use `.strict()`, never `.passthrough()`. Validate enums against CHECK constraints and validate nested objects recursively.
- Tauri v2 IPC parameter naming: Rust `snake_case` maps to JS `camelCase` (e.g. `id_rombel: Option<String>` -> `{ idRombel }`). Passing `snake_case` in JS results in silent `None`.
- Rust string slicing: Never use raw byte slicing `&id[4..10]`. Use UTF-8 safe character iterator `id.chars().skip(4).take(6).collect::<String>()`.
- Full check verification: Always verify completion with `bun run check` (which includes cargo tests), not just `bun run check:quick`.
- Standar Tunggal Waktu Operasional & Tanggal Kanonik WIB: DILARANG menggunakan `date('now')` (UTC) atau `date('now','localtime')` untuk penentuan tanggal operasional, hari ini, filter presensi, rekonsiliasi, maupun snapshot. Antara pukul 00:00–07:00 WIB, query UTC menunjuk ke hari kemarin. Jam server/perangkat WAJIB menggunakan `date('now','+7 hours')` atau `datetime('now','+7 hours')` (mengikuti `current_jakarta_moment` di `scanner.rs`).
- Agregasi Wajib Scan Gerbang Multi-Sesi & Sanitasi Jam Masuk: Tabel `absensi_harian` mengizinkan multi-sesi per tanggal (`izinkan_multi_sesi = 1`). Melakukan join langsung ke `absensi_harian` menggandakan baris siswa dan anomali. Setiap query yang membutuhkan status scan gerbang WAJIB melalui subquery agregasi tunggal (`GATE_SUMMARY_SUBQUERY` / `GROUP BY id_karyawan, tanggal`) dengan `MIN(NULLIF(TRIM(jam_masuk), ''))` dan sanitasi string kosong (`jam_masuk IS NOT NULL AND TRIM(jam_masuk) <> ''`).
- Penolakan Ketat Status Presensi Kelas: Status kehadiran siswa pada presensi mapel terikat ketat pada 5 nilai kanonik: `Hadir`, `Izin`, `Sakit`, `Alfa`, `Dispensasi`. DILARANG mengubah nilai status asing atau error menjadi "Hadir" secara diam-diam (`_ => "Hadir"`). Nilai tak dikenal WAJIB ditolak dengan error validasi (`VALIDATION_ERROR` / HTTP 400).
- Pembersihan Detail Basi Saat Simpan Ulang Sesi Presensi: Saat menyimpan ulang sesi presensi kelas (`save_class_attendance`), backend WAJIB menghapus baris `presensi_mapel_detail` untuk siswa yang sudah tidak ada di roster yang dikirim (misal siswa pindah rombel/keluar), dan mendaftarkan event outbox `delete` untuk detail yang dibuang. Dilarang membiarkan detail usang tetap tersimpan karena akan membuat header `total_*` dan baris detail tidak sinkron serta menghasilkan rekonsiliasi palsu.
- Navigasi Aman & Larangan `redirect("/forbidden")` di Mobile Static Export: Mobile menggunakan Tauri v2 dengan Next.js static export (`output: "export"`) yang tidak memiliki rute `/forbidden`. DILARANG memanggil `redirect("/forbidden")` di mobile. Proteksi area privat di mobile WAJIB menggunakan `useEffect` dengan `router.replace("/dashboard")` untuk pengguna tidak berhak dan `router.replace("/login")` untuk unauthenticated.
- Penghapusan Sesi Presensi Wajib Berizin Sensitif (`class_attendance.delete`): Menghapus sesi presensi mapel memusnahkan seluruh rekam jejak kehadiran kelas jam tersebut. Aksi penghapusan ini WAJIB menuntut permission tersendiri `class_attendance.delete` yang terdaftar dalam `SENSITIVE_MUTATION_PERMISSIONS`, sehingga tidak diberikan secara otomatis ke role bawaan Admin.
- Pengurutan Numerik Jam Pelajaran (`CAST(jam_ke AS INTEGER)`): Kolom `jam_ke` bertipe TEXT sehingga pengurutan leksikografis biasa (`ORDER BY jam_ke ASC`) akan meletakkan jam ke-10 sebelum jam ke-2 (`1, 10, 2, 3...`). Pengurutan sesi dan rekonsiliasi WAJIB menggunakan numerik: `ORDER BY CAST(jam_ke AS INTEGER) ASC, jam_ke ASC`.
- Kesiapan Suara TTS Asinkron & Seleksi Suara Offline (`localService`): Pemanggilan `speechSynthesis.getVoices()` di WebView/Chromium bersifat asinkron dan kosong pada pemanggilan pertama. Modul audio WAJIB mendengarkan event `voiceschanged` dan meng-cache daftar suara. Untuk menjaga kepatuhan offline-first, seleksi suara bahasa Indonesia WAJIB memprioritaskan suara lokal (`voice.localService === true`) agar tidak bergantung pada koneksi internet.

**Immersive 3D / motion UI stack (Desktop + Mobile).** The approved visual stack is fixed: React Three Fiber v9 + drei for real 3D, Spline for no-code hero/mascot scenes, Motion (Framer Motion) for pseudo-3D tilt and layout transitions, Rive for micro-animations and the sync status indicator, vendored Aceternity UI / Magic UI components for spotlight/bento/glow, `detect-gpu` to pick a quality tier, Draco / GLTF-Transform (devDependency only) to compress models, and Zustand purely as a bridge between app data and the canvas. Anything else needs explicit approval. Four constraints dominate every decision here: the app is offline-first so every `.glb`/`.riv`/`.wasm`/decoder/benchmark file must be bundled under `public/3d/` (Rive, `detect-gpu`, Draco, and Spline each default to a CDN and must be overridden, and Desktop's `connect-src` is `ipc:`-only today, so enabling asset fetches plus `'wasm-unsafe-eval'` is a CSP change that needs the user's approval first); `output: "export"` means 3D lives in `src/components/visual/` as `"use client"` modules loaded via `dynamic(..., { ssr: false })` and never imported from `src/lib/**`, which is synced to mobile; GPU capability is detected, never assumed, with tier stored device-local in `localStorage` (`sppg.visual.tier`) — never in the synced `setting_gex_system`; and no WebGL canvas may be mounted on the scanner page while the camera is live, with only one live WebGL context app-wide. Full contract: `.agents/skills/absensi-sppg-rules/references/07-immersive-3d-ui-ux.md`.

**Light/Dark theme harmony & symmetric tone inversion.** All base JSX is strictly dark mode (`bg-slate-900`, `bg-slate-950`, `text-white`, `text-slate-400`); inline light base classes are forbidden. In `web-desktop`, light mode is handled centrally in `globals.css` where all container opacities (`.bg-slate-900\/95`, etc.) must be whitelisted. Light accent text in dark mode (`text-amber-100`, `text-rose-100`) must be symmetrically inverted in light mode to deep high-contrast tones (`#78350f`, `#9f1239`), and critical elements (recovery code pills, bootstrap panels, modals) must carry dedicated semantic classes (`.bootstrap-recovery-code`, `.recovery-code-pill`). In `mobile`, theme inversion is mirrored via `:root[data-theme="light"]` CSS variables (`--color-amber-100: #78350f`).
