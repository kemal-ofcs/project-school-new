# Sync: atribut prioritas, jalur server yang dipensiunkan, gateway Mobile, tarikan inkremental

Dipindahkan APA ADANYA dari `CLAUDE.md` (2026-10-15). Isinya tidak diubah; hanya lokasinya.

**Attendance priority is enforced at the cloud, not just locally.** `apply_event_to_turso` is preceded by `assert_attendance_precondition`, which rejects a push that would overwrite a `Koreksi Admin` row from a lower-priority source, and rejects any event whose `attendanceBaseUpdatedAt` no longer matches the cloud's `update_terakhir`. That field is produced by every client; before this it was simply never read on the Turso path.

**Application-server path retired.** Desktop and Mobile used to have a fourth transport besides the three database providers: when no database was configured they logged in via `POST /api/auth/login` on a Next.js server and synced through `/api/sync/push` + `/api/sync/snapshot` (Rust `remote.rs`, TS `server/operational/sync-push/`, `sync-schema.ts`, `snapshot.ts`). All of it is deleted. That path needed a second, TypeScript implementation of every sync domain and had drifted to 15 of 33 domains — academic events pushed through it were rejected forever. Now every device login and every push/pull goes through `get_turso_client()` (Turso, `sqld`, or the local hub file); a device with no database configured gets `TURSO_NOT_CONFIGURED` (`config::database_not_configured`) and its outbox stays `pending`. `UNCONFIGURED_ORIGIN` (`http://database-belum-diatur.invalid`) replaces the old Vercel URL as the identity key until a database is set. Do not reintroduce an HTTP sync transport. WhatsApp sending has two implementations tested with the same vectors: TS `drainWaQueue` (`wa-sender.ts` + `buatPermintaanProvider` in `wa-provider.ts`) for Web, and Rust `wa_sender.rs` (`desktop_drain_wa_queue`) which sends straight from the device against the configured database — the only sender that exists on `sqld` and local-hub installs. Besides the manual button, `AutoWaSenderRunner` (synced component, mounted in both shells) drains every minute — chaining full 25-row batches — in every session holding `notification.send`; whether it actually sends is decided by the SENDER, which honours the synced setting `wa_kirim_otomatis` (default off) only when called with `otomatis: true`. It runs only while an app is open, and `notification.send` is sensitive, so a scanner terminal that should send must be granted it deliberately. The WA config contract between UI and Rust is camelCase (`WaConfig`/`WaConfigDraft`); Rust once read snake_case keys the UI never sent, so every save from Desktop/Mobile silently switched everything off. Because both may drain the same queue, every row is claimed atomically before sending (`notifikasi_wa.klaim_oleh`/`klaim_sampai`, schema v34, 5-minute lease; final updates are guarded `AND klaim_oleh = ?`), and the cloud upsert of a pushed queue event never moves a final status (`Terkirim`/`Gagal`/`Dibatalkan`) back to `Menunggu`. Without either, a guardian receives the same message twice.

Shared gateways run on both builds, but the two Rust binaries do not register the same commands. A gateway function reachable from mobile UI must branch on `isMobileRuntime()` to a command mobile actually registers; the contract audit walks gateway call graphs from `src/app`/`src/components` to catch this. **Payroll administration is now registered on Mobile too:** `sync-rust-modules.ts` copies `desktop/payroll/{mod,commands,engine,models}.rs` into `mobile/src-tauri/src/mobile/payroll_admin/`, and its 23 `desktop_*` commands (salary configs, components, overtime/tax/BPJS rules, recap, payroll runs and status transitions) are listed in Mobile's `lib.rs`, `build.rs`, and `capabilities/default.json` under their original names — so the gateway's plain `isDesktopRuntime()` branch reaches them and every batch Mobile creates is computed by the exact same `rust_decimal` engine as Desktop. `expectedMobileOnlyUnregisteredCommands` in `audit-sync-contract.ts` is therefore empty; keep it that way. Mobile's payroll recap/estimate also runs through `desktop_get_payroll_recap`; `mobile/src-tauri/src/mobile/payroll.rs` now holds only two read-only slip commands (`mobile_get_my_payroll_slips`, `mobile_get_payroll_slip_detail`, both gated on `payroll.view`). Its old `PayrollCalculator` copy — which ignored holiday hours and minute-exact wages — was deleted: never reintroduce a second money calculator on Mobile. Client-made payroll ids use `new_payroll_id` (`<prefix>-<epoch>-<48-bit random>`); bare epoch-second ids collided inside bulk saves and across devices.

Pulls are incremental: the cloud table `sync_pulse` holds a per-table change counter driven by SQLite triggers, so writes from *any* path — Desktop/Mobile push, the Next.js web route handlers that write straight to Turso, or manual edits — bump it. A sync cycle first probes `sync_pulse`, compares against the local `desktop_sync_table_cursor`, and fetches only the tables whose counters moved (often none). Within a fetched table, rows whose SHA-256 matches `desktop_entity_revision.payload_hash` are skipped without a write. Tables in `sync::APPEND_ONLY_TABLES` (journals, journal lines, inventory and loan mutations, student bills and their cancellations) are pulled INCREMENTALLY instead of whole: cloud trigger `AFTER INSERT` writes each new row into `sync_append_log` (AUTOINCREMENT id, created by `ensure_sync_pulse`, Rust-only like `sync_tombstone`), the device keeps a per-table cursor in `desktop_sync_cursor` (`append:<table>`, saved in the same transaction as the rows), and a pull with a cursor fetches only `sync_append_log.id > cursor` (up to `APPEND_PULL_LIMIT`; a truncated table is left unmarked in `desktop_sync_table_cursor` so the next cycle continues). The cursor is never `rowid` (VACUUM may renumber it on TEXT-PK tables) nor `created_at` (device clock: an offline device pushes "old" rows a pull would skip forever). A table may only join that list if no application ever UPDATEs its rows, since updates do not reach the log; that is why student bills are immutable and cancellation is a separate `keu_tagihan_batal` row. A first pull, a missing log table, or an empty local table falls back to a whole-table pull. A payload key that is absent from a snapshot means "unchanged", not "empty" — `apply_table` must skip it entirely, `delete_missing` included. A failed push never aborts the pull; it is reported via `DesktopSyncStatus.push_error`.
